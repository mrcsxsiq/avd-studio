# Contributing to AVD Studio

Thanks for helping. This page tells you how to get a working setup, what the tests expect, and what a good pull
request looks like. Questions and ideas are welcome as [issues](https://github.com/mrcsxsiq/avd-studio/issues).

By participating you agree to the [Code of Conduct](CODE_OF_CONDUCT.md).

## Before you start

- **Bugs:** open an issue with the bug template. `avdstudio doctor --json` and the app version are the most useful
  things you can attach.
- **Features:** open an issue first for anything bigger than a small fix, so we can agree on the approach before you
  spend time on it. The roadmap is in the README (create devices, install system images, …).
- **Security:** see [SECURITY.md](SECURITY.md). Please do not open public issues for vulnerabilities.

## Setup

You need:

- macOS 14 or newer on an Apple Silicon Mac
- Xcode 16 or newer (Swift 6 toolchain; `swift format` ships with it)
- a JDK 17 or newer, and [XcodeGen](https://github.com/yonaskolb/XcodeGen): `make bootstrap` installs both via Homebrew

```bash
git clone https://github.com/mrcsxsiq/avd-studio.git
cd avd-studio
make bootstrap
make core          # builds the Kotlin core into macos/Frameworks (needed before any Swift build)
make test          # Kotlin + Swift tests
make app           # Release build; `make run` opens it, `make install` copies it to /Applications
```

To work in Xcode: `make generate` creates `macos/AVDStudio.xcodeproj` (not committed) from `macos/project.yml`.
Re-run `make core` after changing Kotlin; Xcode picks up the new framework on the next build.

`make help` lists everything.

## Where things live

| Part | Path | Notes |
| --- | --- | --- |
| Logic | `core/src/commonMain/kotlin/dev/marcos/avdstudio/core` | Kotlin Multiplatform, no UI. `AvdStudioCore.kt` is the façade. |
| CLI | `cli/src/macosMain/kotlin/dev/marcos/avdstudio/cli` | Clikt commands; `Output.kt` formats tables, doctor output and JSON. |
| UI | `macos/Sources/AVDStudioUI` | SwiftUI views, `AppModel`, `UpdateModel`, `SetupModel`. No Kotlin here. |
| Bridge | `macos/Sources/AVDStudioKit/KotlinDeviceService.swift` | The only Swift file that imports the Kotlin framework. |
| App | `macos/App` | `AVDStudioApp.swift`, asset catalog (icon generated by `make icon`). |
| Website | `website/` | Static; see `website/README.md`. |

[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) explains how the pieces talk to each other and why.
[AGENTS.md](AGENTS.md) has the rules in checklist form (written for AI agents, useful for everyone).

## Tests

Three suites, all run by CI:

| Suite | Command | What it covers |
| --- | --- | --- |
| Kotlin | `make test-kotlin` | Core (fake file system, recording command runner) and CLI (temp folders, fake `brew`/`sdkmanager`). |
| Swift unit + bridge | `make test-unit` | `AppModel`, `UpdateModel`, `SetupModel`, models and theme with `FakeDeviceService`; the bridge against the real core in a temporary home. |
| Screenshots | `make test-swift` | Every screen, light and dark, with `swift-snapshot-testing`. |

Rules:

- A change in behaviour comes with a test in the same PR. Fixing a bug? Add the test that would have caught it first.
- Tests must be hermetic. They may not read `~/.android`, a real Android SDK, Java or Homebrew. Use the fakes, temp
  folders and the `HOMEBREW_PREFIX` redirect you will find in the existing tests.
- Run `make lint` before pushing (ktlint and `swift format --strict`; `make format` fixes most things).

### Screenshot tests

References live in `macos/Tests/AVDStudioSnapshotTests/__Snapshots__` and are compared pixel-by-pixel with a small
tolerance.

- First run on a new machine: the missing references are recorded and the run fails once. Run it again.
- Changed a view on purpose? `make record-snapshots`, open the PNGs, check they look right, commit them (ideally in
  their own commit). Describe the visual change in the PR.
- A screenshot test failing when you did not touch that view is a regression to investigate, not a reason to
  re-record.
- On CI the job is informational for now: text rendering differs between macOS versions, so references recorded on a
  developer Mac may not match the runner image. The job uploads the failing images as an artifact so you can look.

## Pull requests

1. Branch from `main`. Keep one logical change per PR.
2. Follow the code style that is already there: Kotlin with `explicitApi()` and warnings as errors; Swift 6 with
   strict concurrency, `@Observable` models, Apple's terminology in UI strings (Settings, menu bar, Finder).
3. Commit messages follow [Conventional Commits](https://www.conventionalcommits.org): `feat(core): …`,
   `fix(cli): …`, `docs: …`, `ci: …`, `build(deps): …`. Explain *why* in the body when it is not obvious.
4. Update `CHANGELOG.md` under `## [Unreleased]` for anything a user can notice, `LICENSES.md` when a dependency
   changes, and the README when a command or setting changes.
5. Fill in the PR template: what, why, how you tested it (real output), and screenshots for UI changes.
6. CI must be green. A maintainer reviews, may ask for changes, and squashes or rebases on merge.

## Dependencies

Dependabot opens weekly PRs for Gradle, Swift packages and GitHub Actions. Adding a dependency is a conversation:
open an issue first, prefer the standard library, and remember the app ships to people's Macs. Any new dependency
goes into `LICENSES.md` with its licence.
